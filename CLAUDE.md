# TrayTweaks: notes for Claude sessions

Jesse's personal Windows tray utility (WPF, .NET 10) that hosts small Windows tweaks. The README covers what it does, how to build it and how to add a tweak. This file holds what the README doesn't: working rules and the list of open items. Keep the open items current: remove one when it is done, add one when something is left unfinished or unverified.

## Working rules

- Personal project, not tied to a Jira ticket: commit subjects have no ticket key. Work on `main`, no branches or PRs.
- The repo is public. The repo-local `user.email` is Jesse's GitHub noreply address; leave it that way so a work email never lands in a public commit.
- The app's manifest is `requireAdministrator`, on purpose: Jesse is moving his AutoHotkey scripts into it and those need admin. Start it from an elevated shell (a normal `dotnet run` fails with error 740). Anything the app launches is elevated too.
- Jesse's AutoHotkey scripts (repo `autohotkey-script`: `Jesse.ahk`, `Automater.ahk`) are being replaced piece by piece: he asks for a feature when he notices he misses it. Don't port them wholesale. They contain passwords: never copy a password, or any script text that includes one, into this public repo, a commit message or a chat reply. Password-typing macros get their text from the Passwords tab in Settings, which keeps it in `%LocalAppData%\TrayTweaks\secrets.json`, encrypted with DPAPI (`Secrets/SecretStore.cs`); never in source, in `settings.json` or in a synced file. Jesse types the text in himself. Tests use a throwaway store file and dummy text, never the real store or a real password.
- Exit the running TrayTweaks (tray menu > Exit) before rebuilding, or the build can't overwrite the exe. If you end the process instead, a ghost tray icon stays until the mouse passes over it.
- Never start the app from Claude's shell (`Start-Process`, `dotnet run`, running the exe). Start it with `Start-ScheduledTask -TaskName TrayTweaks` (the sign-in task; it works from a non-elevated shell and runs the Debug build elevated) and stop it with `Stop-ScheduledTask -TaskName TrayTweaks`. The Claude desktop app is a packaged (MSIX) app, and Windows redirects AppData writes made by anything started from it, elevated or not, into the package's private storage (`%LocalAppData%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Local` and `...\Roaming`). A copy of TrayTweaks started from Claude therefore saves `settings.json` and `secrets.json` where the real app never looks, and it dies without a trace when the Claude app restarts or updates. Both happened: on 2026-11-23 the app vanished, and the login Jesse had saved on 2026-11-21 showed as "Not set" in the task-started copy until `secrets.json` was copied from the package folder to the real `%LocalAppData%\TrayTweaks`.
- For the same reason, what Claude's shell shows under `%AppData%\TrayTweaks` and `%LocalAppData%\TrayTweaks` is a merged view, with the package's stale copies hiding the real files. Don't trust it for what the app sees. Read `%LocalAppData%\TrayTweaks\log.txt` instead (the app logs at startup who it runs as and whether each secret is readable; a file the real app wrote shows through), or run a check outside the redirection: a process started through Explorer, which is what `Input/UnelevatedLauncher.cs` does, sees the real folders. Throwaway test projects started from Claude's shell have the same redirected view, so a test that touches "the real store" is touching the package's copy.
- To check how a window looks without using Jesse's screen: a throwaway WPF console project that references the app project, creates a plain `Application` with `ThemeMode` set (not `TrayTweaks.App`, whose startup would create a tray icon), shows the window off-screen, renders `window.Content` with `RenderTargetBitmap` to a PNG, and reads the PNG. Stop the running app first, because building the reference rebuilds its exe.
- Toggle tweaks are on by default, and so is every tweak added later, unless Jesse says otherwise for that tweak (his instruction, 2026-11-23). The one exception so far is Keep Outlook running, which is for his work PC only. So don't override `OnByDefault` on a new tweak unless he asks, and don't tell him to tick a new tweak in Settings: it is already on after the app restarts. `settings.json` holds only his explicit choices.
- Icons are glyphs that must exist in both Segoe Fluent Icons (Windows 11) and Segoe MDL2 Assets (Windows 10). Check both font files before using a new one.
- Tray menu items are deliberately not `IsCheckable`: the Fluent theme gives checkable items their own column, which pushes the other items' icons out of place. The checkmark goes in the icon slot.
- Never run `ExplorerTabCombiner.CombineStacked()` unfiltered while testing; it would rearrange Jesse's real Explorer windows. Open throwaway Explorer windows and pass the `include` filter so only those are touched, and close them afterwards. The earlier test harness was a throwaway console project that linked `ExplorerTabCombiner.cs`, opened four windows on temp folders, stacked three with `SetWindowPos`, combined, and checked the result through `ListTabs()`.

## What was learned about Explorer tabs (Windows 11 build 26300)

- New tab in a specific window: post `WM_COMMAND` `0xA21B` to one of the window's `ShellTabWindowClass` children. Undocumented, so recheck after big Windows updates.
- Navigating a new tab before it finishes loading its default folder gets lost or lands in the wrong tab. `OpenTab` waits for the tab to be idle, navigates, then verifies.
- `Navigate2` rejects a bare `::{guid}` path (This PC, Home); it needs `shell:` in front.
- `WM_CLOSE` on a multi-tab Explorer window closes only the active tab, so `CloseWindow` repeats it.

## Mouse buttons (Logitech G604)

- The G604 is in onboard-memory mode, so the button mapping lives in the mouse. G HUB's `settings.db` only holds placeholder software profiles and does not show it. The true map has to come from G HUB's Onboard Memory Manager screen or from pressing each button.
- The mouse has 16 assignable controls and two layers (default, and G-Shift held). The only profile Jesse uses is "Hybrid MF". Its map, read from Logitech Onboard Memory Manager screenshots on 2026-11-20:

  | Button | Default | With G-Shift held |
  |---|---|---|
  | 1 | Left click | Ctrl+= |
  | 2 | Right click | Ctrl+- |
  | 3 | Middle click | Media key (which one not recorded) |
  | 4 | F13 | F17 |
  | 5 | G-Shift | G-Shift |
  | 6 | Forward (Mouse 5, `XButton2`) | Back (Mouse 4, `XButton1`) |
  | 7 | F14 | F18 |
  | 8 | Alt+F4 | F19 |
  | 9 | Ctrl+W | F20 |
  | 10 | F15 | F21 |
  | 11 | F16 | F22 |

  | 13 | Tilt Right | F24 |
  | 14 | Scroll Down | Media key (which one not recorded) |
  | 15 | Scroll Up | Media key (which one not recorded) |
  | 16 | No Action | No Action |

- Physical positions. Buttons 4 to 9 are the six thumb buttons, which have G4 to G9 printed on them; the number matches the label. Seen from the left side with the front of the mouse to the left, the top row is G9, G8, G7 and the bottom row is G6, G5, G4. So button 5 (G-Shift) is bottom centre, which is what Jesse said, and button 6 (Forward by factory default and in his profile) is bottom front. Buttons 1 to 3 are left, right and wheel click; 12 to 15 are the wheel tilts and scroll directions. Beside the left click, button 10 is the - button and button 11 is the + button (Jesse checked with Identify Button). Button 16 is unidentified (No Action on both layers). The number-to-label match is inferred from those two agreeing points and a review photo, not from Logitech documentation.
- He rarely remaps, but can, so treat this table as a snapshot. The same data is in `src/TrayTweaks/Mouse/MouseMap.cs`, which feeds the Mouse tab in Settings; keep the two in step.
- The AutoHotkey scripts have a hotkey for every one of F13 to F24 and for `XButton1` / `XButton2`. Those two are also what his smaller mice send from their side buttons, so mouse features must keep working with a plain two-side-button mouse.
- To list the scripts' hotkeys without exposing what they type, print only the trigger and the command word of each action, never the arguments.

Jesse wanted far more see-through than Mica or Windows' acrylic, in the direction of Aero glass; he called this version "pretty awesome". He tried a tint slider, liked it all the way up, and asked for it to be fixed there with no option, so there is no setting. Because nothing tints the glass, it can come out light or dark (over a white window it is mid grey), and the XAML allows for that: nothing readable sits straight on the glass. The TabControl template in `SettingsWindow.xaml` draws two frosted islands (`FrostBrush`, the theme's window colour at 60%, rounded, with a faint light edge): the tab bar, with the selected tab as a bright pill in it, and one island per tab page. Panels on a page use `PlateBrush` (the same colour at 70%) instead of the theme's card brush, which is nearly transparent in dark mode. Keep that when adding UI to this window: text goes on an island, never on bare glass. How it got there, on 2026-11-23: text on bare glass was unreadable over a dark window; a white glow behind it was too faint; five stacked glows were readable but Jesse found the result "weird" and asked for "a frosty island" instead; and he had found the Fluent theme's unselected tab names "floating in space", wanting them to sit in something, as they would with Apple's liquid glass. It took five tries; what was learned, so nobody repeats them:
  - The DWM acrylic backdrop (`DWMSBT_TRANSIENTWINDOW`) can't be adjusted and turns flat grey when the window loses focus.
  - The undocumented `SetWindowCompositionAttribute` accent works, focused or not, but only after the system backdrop is set to none and `DwmExtendFrameIntoClientArea` is called with zero margins. The Fluent theme extends the frame over the whole window, and that frame hides the accent.
  - Accent state 4 (acrylic blur) adds its own milky layer, so its tint alpha changes almost nothing and it washes out to flat white over a light window. Jesse found it less glassy than DWM acrylic.
  - Accent state 2 (tint, no blur) follows alpha exactly, but he did not like sharp content showing through.
  - Accent state 3 (blur) with `AccentFlags = 0` is the one in use: strong blur, no tint, colour ignored. With the usual flags value 2 it renders black on this build.
  - The window has no native title bar (2026-11-23, at his request): the row holding the tab bar is the title bar, with minimize and close in their own island at the top right. It is `WindowStyle="None"` plus a `WindowChrome` whose `CaptionHeight` covers that row. What was learned getting there: a framed window with `WindowChrome` turns its invisible resize border into drawing area, so the glass spills about 8 px past the visible edge with square corners; `NonClientFrameEdges` does not fix that, it paints those edges solid white; a frameless window is the right size but needs `DWMWA_WINDOW_CORNER_PREFERENCE` set to round, which `WindowBackdrop.Apply` does. Anything clickable inside the caption strip needs `WindowChrome.IsHitTestVisibleInChrome`, and the tabs need it in the TabItem style, because a tab inherits the property from the TabControl and not from the bar drawn around it. Before this change the native title bar was solid in his accent colour while focused.
  - Checked on the test card in light and dark theme, both tabs, focused, and on 2026-11-23 the islands over a dark test card in light theme, all three tabs, plus off-screen renders in light and dark. The custom title bar was checked the same day by asking the window, with `WM_NCHITTEST` and no input sent, what is under five points (tabs, both buttons and a checkbox are clickable, the empty part of the top row drags) and by raising the two buttons' click events. Not checked: a real drag with the mouse, and how the frameless window looks on Windows 10, where there is no glass, no rounded corners and probably no shadow or border. Not checked: dragging the window, a theme switch while it is open, and Windows 10 (where the glass is skipped and the window should be solid; Jesse said "at some point, we'll go see how it looks on Windows 10").
